Section 1. Databricks Intelligence Platform (6%)

Core components: architecture, Delta Lake, Unity Catalog

  • Lakehouse: one copy of data with warehouse features on open lake storage; BI and engineering teams share the same source of truth. Open source means no vendor lock-in.
  • Control plane (Databricks account): web app, notebooks and repos, job scheduler, compute orchestration, Unity Catalog. Compute plane: clusters, SQL warehouses, serverless that run the code. Your cloud storage: the data. A scheduled notebook is stored (encrypted) in the control plane and executes in the compute plane.
  • Delta Lake = Parquet files + _delta_log (JSON commits, checkpoints). ACID, schema enforcement and evolution, time travel, batch and streaming on one table. The file format answer is Parquet, not "Delta".
  • Unity Catalog = governance (permissions, lineage, audit, discovery, tags, ABAC). Delta Lake = storage layer. They are not interchangeable.
  • Medallion: Bronze = raw, append-only, schema applied, plus load time/source file. Silver = cleaned, deduplicated, conformed, joined. Gold = aggregated, denormalized, read-optimized for BI.

  • Databricks Connect: IDE on your laptop, Spark work runs remotely (proxies Spark Connect commands). Match Python minor version for UDFs and use a Connect version compatible with the runtime. Serverless needs Unity Catalog and a supporting client version.
  • Lakehouse Federation queries external databases in place (governed by UC). Delta Sharing shares data out.

Batch, streaming, incremental patterns

  • Batch: spark.read, COPY INTO, JDBC. Incremental: Auto Loader/COPY INTO track processed files. Streaming: readStream with checkpoints. Auto Loader with trigger(availableNow=True) = incremental batch.
  • Kafka + Snowflake mock: Structured Streaming for Kafka and a Lakeflow Connect managed connector in incremental mode.

COPY INTO into Unity Catalog tables

COPY INTO main.lab.target
FROM '/Volumes/main/lab/landing/orders'
FILEFORMAT = JSON
COPY_OPTIONS ('mergeSchema'='true');
  • Idempotent per file path: loaded files are skipped, even if re-uploaded under the same name (mock: load corrections as new files and update the target). FORCE=true reloads and can duplicate.
  • Zero rows added = the file was already loaded. Format goes in FILEFORMAT; FORMAT_OPTIONS only tunes parsing.

Auto Loader: enforcement, evolution, modes

(spark.readStream.format('cloudFiles')
  .option('cloudFiles.format','json')
  .option('cloudFiles.schemaLocation','/Volumes/main/lab/landing/_schema')
  .load('/Volumes/main/lab/landing/orders')
  .writeStream.option('checkpointLocation','/Volumes/main/lab/landing/_chk')
  .trigger(availableNow=True).toTable('main.lab.bronze'))
  • Built on Structured Streaming; the checkpoint remembers files, so only new files are read. A File Arrival job trigger just starts the job.
  • JSON/CSV columns default to STRING unless cloudFiles.inferColumnTypes=true or cloudFiles.schemaHints.
  • cloudFiles.schemaEvolutionMode: addNewColumns (default; fails once, then adds a nullable column), rescue (_rescued_data), failOnNewColumns (fails until fixed), none.
  • Detection mode: directory listing (default) vs file notification/file events (scales to very large directories; mock key prefers notification for 50,000+ existing files).
  • pathGlobfilter (e.g. *.png) restricts file names.

Lakeflow Connect (reliable enterprise ingestion)

  • Managed connectors: UI/API setup, serverless, CDC, schema evolution, OAuth, retries, monitoring, land in UC Delta tables. Use separate connectors per source and per-source UC schemas for lineage; keep Delta table history for audits.
  • 50+ Salesforce objects, SQL Server CDC, daily ADLS JSON: managed connectors for the first two, Auto Loader for the files, all in Lakeflow Spark Declarative Pipelines.

Semi-structured and nested data

  • JSON string: get_json_object(col,'$.user.id') or from_json(col, schema). Struct: col.* flattens one level only; a.b.c goes deeper. Arrays: explode, filter, transform. Kafka value is binary: CAST(value AS STRING).
  • Kafka: format('kafka'), kafka.bootstrap.servers, subscribe, startingOffsets. Not cloud_files.
Section 3. Data Transformation and Modeling (22%)

Cleaning bronze to silver

  • Drop null rows: df.dropna(subset=[...]) (how='any' default; 'all' only if all are null). Standardize types with cast. Write to a new Delta table (saveAsTable / streaming toTable).
  • Columns/rows: withColumnRenamed, withColumn, drop, split(col, ','), explode(arr), filter/where.

Deduplication and aggregation

  • df.dropDuplicates(['id','email']) keeps one row per key; dropDuplicates() / distinct() compare all columns.
  • df.groupBy('k').agg(sum('a'), avg('a'), max('a')) (alias inside agg). Also count, approx_count_distinct('col'), df.summary('count','mean','stddev'). count(col) ignores NULLs; count(*) counts rows; count_if(cond) counts true conditions. Null-safe equality: <=>.
  • Rolling windows and top-N: window functions. Percent of total: groupBy total + join, or a window over everything.

Data quality (Silver and Gold)

  • Expectations in Lakeflow Spark Declarative Pipelines (formerly DLT): CONSTRAINT n EXPECT (cond) alone = keep and record; ON VIOLATION DROP ROW = drop and record in the event log; ON VIOLATION FAIL UPDATE = stop the update. Per-table drops: pipeline UI data quality tab / event log.
  • CREATE STREAMING TABLE (formerly CREATE STREAMING LIVE TABLE) reads with STREAM(src); CREATE MATERIALIZED VIEW (formerly CREATE LIVE TABLE). One pipeline can mix Python and SQL files.
  • Streaming basics: availableNow vs processingTime='5 seconds'; checkpoint + write-ahead log record offsets; raw to Bronze = readStream.load append; Silver to Gold = groupBy/agg.
  • Delta: schema enforcement, CHECK/NOT NULL constraints, MERGE (WHEN NOT MATCHED BY SOURCE THEN DELETE).
Section 4. Working with Lakeflow Jobs (16%)

Tasks and the DAG

  • Task types: notebook, SQL query, dashboard, pipeline, Python script/wheel, run job, if/else condition, for each. Each task lists Depends on; a new prerequisite is a new task that the original task depends on.
  • Fan-out: several tasks depend on one. Fan-in: one task depends on several and waits for all (default Run if = All succeeded).
  • Run if: All succeeded, At least one succeeded, None failed, All done, At least one failed, All failed. "C only if A succeeded and B failed" = A with All succeeded plus B with At least one failed (mock key).

Control flow

  • Retries and timeouts per task. Branching: If/else condition task reading task values (dbutils.jobs.taskValues.set/get, {{tasks.name.values.key}}). Looping: For each task.
  • Repair run re-runs only failed/skipped tasks (and dependents), keeps successful results, uses current settings, same run history; API repairRun. "Run now" creates a brand new run.
  • max_concurrent_runs (default 1) explains skipped/queued runs.

Schedules and trigger types

TriggerFires whenChoose when

  • 15-minute SLA with small increments: scheduled every ~12 min running an availableNow stream. Time-based = predictable; data-driven = efficient for irregular or upstream-dependent data.
  • SQL side: refresh schedules (with an end date), alerts with webhook destinations, warehouse Auto Stop.

Section 6. Troubleshooting, Monitoring, and Optimization (10%)

Run history and job health

  • Run history: compare each run's duration with the baseline, see whether slowdown is every run or intermittent, then open compute metrics of slow runs. Do not reset baselines or scale blindly.
  • Job statuses, DAG task graph (find the upstream task that failed/blocked), run times and failure rates; open a task from the active run to see its notebook and compute.

Spark UI: skew, shuffle, spill

SymptomReadingFix
Stage tasks: median 45 s, max 80 sData skewBetter repartition key, salting, AQE skew join
Large shuffle read/writeWide transformation costBroadcast small side, filter early, tune shuffle partitions
Memory spill to diskPartitions too big for memoryMore shuffle partitions first (cheapest), then memory
Executor OOM / ExecutorLostFailure in a joinShuffle memory exhaustionMore shuffle partitions or executor memory
Driver OOM after collect()/toPandas()Too much data on the driverAvoid collecting, aggregate first, or raise driver memory
High CPU time vs task time (V3.2 key)CPU-bound jobTune cores/executors or resize
  • Spark UI (Jobs, Stages, Executors) is the starting point for stage and task metrics. Ganglia/cluster metrics are coarse. Serverless has no Spark UI; use the query profile.

Liquid clustering and predictive optimization

  • Liquid clustering: CLUSTER BY (cols) at creation or ALTER TABLE ... CLUSTER BY (...) later; replaces partitioning and ZORDER; suits high-cardinality filters and changing query patterns; CLUSTER BY AUTO lets Databricks choose keys. Cannot be combined with partitioning/ZORDER. Clustering is applied by OPTIMIZE.
  • Predictive optimization: enable at account/catalog/schema; automatically runs OPTIMIZE, VACUUM, ANALYZE on UC managed tables. Verify manual OPTIMIZE with DESCRIBE HISTORY.
  • OPTIMIZE is idempotent. VACUUM removes unreferenced files (default 7 days) and ends time travel to them.

Cluster startup failures, library conflicts, OOM

  • Startup failures: read the cluster event log and error: cloud quota/capacity, bad instance type or subnet/IP exhaustion, init script failure (init script logs), spot capacity. Pools or serverless shorten startup.
  • Library conflicts: cluster-scoped vs notebook-scoped (%pip) versions, pins vs runtime-bundled packages, wheels built for another Python minor version. Pin versions, restart the Python process, use a clean environment.
  • OOM: decide driver (collect, toPandas) vs executor (shuffle, skew, wide joins) and adjust the matching setting.
Section 7. Governance and Security (15%)

Managed vs external tables

ManagedExternal
StorageUC-managed location (metastore/catalog/schema)LOCATION path under an external location
DROPMetadata and data removed (UNDROP for a retention window)Metadata only; files stay
BenefitsAutomatic optimization/cleanup, predictive optimization, name-based accessFiles shared with systems outside Databricks
ConvertALTER TABLE t SET MANAGED converts external to managed in place (same name, permissions, history)Managed to external: recreate with LOCATION (CTAS/copy)
  • Creating an external location needs CREATE EXTERNAL LOCATION on the metastore and on the storage credential. Restart streaming readers after a conversion.
  • Hive metastore legacy: CREATE TABLE ... LOCATION = external; default database location dbfs:/user/hive/warehouse.

Access control: GRANT, REVOKE, DENY

  • Hierarchy: metastore > catalog > schema > table/view/volume/function. Read a table: USE CATALOG + USE SCHEMA + SELECT. Create tables: CREATE TABLE on the schema (plus USE on parents). Least privilege: do not add MODIFY, CREATE SCHEMA or ALL PRIVILEGES unless required.
  • GRANT priv ON obj TO principal / REVOKE priv ON obj FROM principal. Principals: users, groups, service principals (prefer groups). DENY is an explicit block that overrides grants in the legacy table-ACL model; in Unity Catalog, manage access with minimum grants, REVOKE, and policies.
  • Views: consumers need SELECT on the view only; if "insufficient permissions" persists, check catalog, then schema, then view. Hive metastore: GRANT USAGE ON DATABASE.
  • Ownership: owners manage grants on the object and children; transfer schema ownership (or grant MANAGE) to delegate without workspace admin. Find the owner on the table page or DESCRIBE EXTENDED. SHOW GRANTS ON TABLE t lists privileges.

Row filters, column masks, ABAC

CREATE FUNCTION main.secure.region_filter(region STRING)
RETURN IF(is_account_group_member('all_regions'), true, region = 'EU');
ALTER TABLE main.secure.events SET ROW FILTER main.secure.region_filter ON (region);

CREATE FUNCTION main.secure.mask_ssn(v STRING)
RETURN IF(is_account_group_member('hr'), v, '***-**-****');
ALTER TABLE main.secure.people ALTER COLUMN ssn SET MASK main.secure.mask_ssn;
  • Create the function first, then attach: row filter returns BOOLEAN (SET ROW FILTER fn ON (cols)); mask returns the column value (ALTER COLUMN c SET MASK fn). Not on views. Key caution: the V3.2 row-filter key shows only the function; it still must be attached with SET ROW FILTER.
  • ABAC: put governed tags on columns/tables and define a policy once (e.g. on a catalog); it applies row filters/masks to all matching current and future objects without per-table setup.

Lineage, sharing, audit

  • Lineage is automatic and shows tables, columns, notebooks, jobs, pipelines and dashboards (V3.2 "table-level only" key is wrong). Audit logs are JSON. DESCRIBE HISTORY shows who changed a table.
  • Delta Sharing: open protocol for non-Databricks recipients (read-only, no account); Databricks-to-Databricks needs the recipient's metastore sharing identifier. Cross-cloud/region adds egress; Cloudflare R2 avoids it (V3.2 key says otherwise). Internal write access is controlled by UC grants.
Key cautions in the mocks: V3.2 DLT migration ("entirely Python") is excluded here; V3.2 lineage; V3.2 PySpark agg with strings; V3.2 Delta Sharing egress; V3.3 debugger wording (variable explorer is the real feature); V3.3 job output limit (10 MB, verify in docs); "Repair the task" (V3.2) vs "Repair the run" (V3.3).

Lab 15. Delta basics: time travel, MERGE, OPTIMIZE, VACUUM, liquid clustering
%sql
CREATE OR REPLACE TABLE students (id INT, name STRING, score INT);
INSERT INTO students VALUES (1,'ana',70),(2,'ben',80),(3,'cy',90);
UPDATE students SET score = 95 WHERE id = 3;
DELETE FROM students WHERE id = 2;
DESCRIBE HISTORY students;                     -- versions, users, operations
SELECT * FROM students VERSION AS OF 1;        -- before UPDATE/DELETE
SELECT * FROM students@v1;                      -- same, @v syntax
RESTORE TABLE students TO VERSION AS OF 1;     -- roll back
DESCRIBE DETAIL students;                      -- numFiles, sizeInBytes, clusteringColumns

MERGE (upsert, delete rows missing from the source):

%sql
CREATE OR REPLACE TEMP VIEW updates AS
SELECT * FROM VALUES (1,'ana',75),(4,'dee',60) AS t(id,name,score);

MERGE INTO students t USING updates s ON t.id = s.id
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *
WHEN NOT MATCHED BY SOURCE THEN DELETE;
SELECT * FROM students;

Small files, OPTIMIZE, VACUUM:

%sql
INSERT INTO students VALUES (10,'x',1); INSERT INTO students VALUES (11,'y',2);  -- many tiny files
OPTIMIZE students;      -- run twice: second run does nothing (idempotent)
DESCRIBE HISTORY students;   -- find the OPTIMIZE rows
VACUUM students DRY RUN;     -- lists files; default retention is 7 days

Liquid clustering:

%sql
CREATE OR REPLACE TABLE events (id BIGINT, customer_id STRING, event_date DATE) CLUSTER BY (customer_id);
INSERT INTO events SELECT id, CONCAT('c', id % 50), current_date() FROM range(100000);
OPTIMIZE events;
DESCRIBE DETAIL events;                           -- see clusteringColumns
ALTER TABLE events CLUSTER BY (customer_id, event_date);   -- change keys, no rewrite needed
ALTER TABLE events CLUSTER BY AUTO;               -- automatic keys (needs predictive optimization)
What to observe: WHEN NOT MATCHED BY SOURCE removed id 3 (not in updates). VACUUM is what ends time travel. Liquid clustering replaces PARTITIONED BY / ZORDER and can be re-keyed with ALTER. Predictive optimization is a setting on schema/catalog/account (Catalog Explorer > schema > Details) and runs OPTIMIZE/VACUUM for you on managed tables.
